# Translation

The framework is written in English and ships a **French** catalog:
every string of its pages, its forms, its tables and its JavaScript. It
is Django's own machinery — `gettext`, `.po` files, `.mo` files — with
two additions: the language a project offers is a list it narrows, and
the language a person reads is a preference that follows their account.

```
generic/locale/fr/LC_MESSAGES/django.po     315 strings (Python, templates)
generic/locale/fr/LC_MESSAGES/djangojs.po   299 strings (the browser)
example/locale/fr/LC_MESSAGES/django.po     210 strings (the example app)
```

## Wiring a project

```python
# settings.py
LANGUAGE_CODE = "en-us"
# Narrow this to what you actually translated: left alone it holds every
# language Django ships, and the frame then offers no menu at all.
LANGUAGES = [("en", _("English")), ("fr", _("French"))]
LOCALE_PATHS = [BASE_DIR / "locale"]      # your own catalogs
USE_I18N = True

MIDDLEWARE = [
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.locale.LocaleMiddleware",          # after the session
    "django.middleware.common.CommonMiddleware",
    ...
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "generic.middleware.UserLanguageMiddleware",          # after the auth
    ...
]
```

```python
# urls.py - the browser's catalog, or the JavaScript stays English
path("jsi18n/",
     JavaScriptCatalog.as_view(packages=["generic"]),
     name="javascript-catalog"),
```

`generic/base.html` loads that route when it exists, under the name
`javascript-catalog`. Add your own app to `packages` once you translate
strings in your own JavaScript.

## How a page picks its language

| In order | Decided by |
| --- | --- |
| The signed-in user's preference | `UserLanguageMiddleware`, from `UserPreferences.language` |
| The `django_language` cookie | Django's `LocaleMiddleware`, set by the language menu |
| `Accept-Language` | the browser |
| `LANGUAGE_CODE` | the project |

The preference follows the account, so the same person reads French on
a colleague's machine; the cookie covers visitors who have not signed
in. A preference naming a language the project no longer offers is
ignored rather than obeyed.

## Choosing a language

Two ways, both built in:

- **The account menu** — a *Language* section listing `LANGUAGES`, with
  the active one ticked. It posts to `site:set_language`, which saves
  the preference, sets the cookie and comes back to the page. A form,
  not a script: it works before anything has loaded.
- **Account › Preferences** — the same choice as a field of the
  preferences form, saved through `api/generic/account/preferences/`.
  Empty means *follow the browser*.

Both refuse a language outside `LANGUAGES`; the endpoint answers 400,
the menu ignores it.

## Working on the catalogs

The usual Django commands, from the repository root:

```bash
django-admin makemessages -l fr --domain django   --ignore .venv
django-admin makemessages -l fr --domain djangojs --ignore .venv --ignore "*/vendor/*"
django-admin compilemessages --ignore .venv
```

Both need GNU gettext (`xgettext`, `msgfmt`) — `apt-get install gettext`,
`brew install gettext`, or the installer on Windows. When it is not
there, the compilation step alone has a fallback with no dependency:

```bash
python scripts/compile_messages.py            # every .po of the repository
python scripts/compile_messages.py --check    # fail if a .mo is stale
```

It reads what these catalogs use — the header, plain entries, plurals,
contexts and the usual escapes — and refuses anything else rather than
guessing.
CI runs `--check`, and the suite asserts the same thing
(`tests/test_i18n.py`), because a `.po` edited without recompiling
translates nothing and says nothing.

**The `.mo` files are committed.** They are what the application reads;
a checkout without them runs in English, and a demo that needs a build
step to speak French is a demo that does not.

## Adding a language

1. Add it to `LANGUAGES`.
2. `django-admin makemessages -l de` for both domains, translate the
   `.po` files, compile them.
3. Nothing else: the menu, the preference and their validation all read
   `LANGUAGES`.

To translate the framework itself rather than your project, put the
`.po` under `generic/locale/<code>/LC_MESSAGES/` — or keep your own copy
under `LOCALE_PATHS`, which Django reads first.

The example application is translated the same way, in its own catalog
(`example/locale/`), and is worth reading as the pattern for an
application: model verbose names, choice labels with their context,
resource declarations, actions and the pages of its feature guide.

## Writing translatable code

| Where | How |
| --- | --- |
| Declarations (resources, models, choices) | `gettext_lazy as _` — evaluated per request, not at import |
| Views, actions, messages | `gettext` — the language is known by then |
| Templates | `{% translate %}` and `{% blocktranslate %}` |
| JavaScript | `Generic.t("…")`, `core.t("…")` in the table code |
| Plurals | `ngettext(singular, plural, count)`, both forms in the catalog |

Interpolate with named placeholders — `%(count)s`, never `%s` — so a
translator can move them. In JavaScript, `Generic.format()` and
`core.format()` do the same with `%(name)s`.

A string only reaches the catalog if `makemessages` can see it: a
message built by joining fragments at runtime cannot be translated, and
a `_("…")` sitting on a module-level constant is evaluated once, before
anyone has asked for a language. `gettext_lazy` is the answer to both.

### The same word, two meanings

A catalog is keyed on the English string, so one word can hold one
translation — and the catalogs of the framework and of an application
are merged into one. *Open* is the framework's row action (*Ouvrir*)
and a ticket's state in the example (*Ouvert*); left alone, one of them
wins everywhere and reads as nonsense in the other place.

The fix is a context, which becomes part of the key:

```python
from django.utils.translation import pgettext_lazy

class Status(models.TextChoices):
    OPEN = "open", pgettext_lazy("ticket status", "Open")
```

Use one whenever a short label could mean something else elsewhere —
states, one-word column titles, menu verbs. Do not rely on which
catalog wins: it is an ordering detail, not a rule.

## What is not translated

Rows in the database — ticket titles, customer names, the seeded tags —
are content, not strings: they read as they were written, in any
language. Django's own strings (the admin, form validation, date
formats) come from Django's catalogs, which already cover French.
